二、核心决策（架构划分与边界判断）

2.1 总纲：判断交给 LLM，事实与纪律交给代码

整个系统只有一条铁律：所有"硬要求"必须落在确定性校验层（落盘前拒绝 + 报错引导自我修正）， prompt 只做战术引导。prompt 能降低出错概率，校验才能保证下限——这条铁律在实践中被 真实事故反复验证（§四）。

职责归属为什么
行情拐点判定代码（确定性算法） 拐点是可定义的数学事实（趋势拐头/加速/回撤/量能异常，每个点带触发规则与数据窗口）。 LLM 判拐点不可复现、不可审计；算法宁多勿漏 + severity 分级，筛选权留给下游判断
事件发现LLM 决策 + 代码执行 "往哪个方向查、查什么关键词"是判断（LLM，围绕拐点时间窗带着问题检索）； "检索本身"是确定性 HTTP API（Tavily/HN/Yahoo，不经 LLM 转述——换模型不改变检索数据）。 检索次数有确定性预算，耗尽强制收敛
拐点×事件归因LLM 论证 + 契约约束 归因本质是论证，交给独立的 alignment-analyst（零检索工具，只基于给定材料，可复现性最好）； 但结论被契约收窄为 match/partial/none 枚举 + "时间吻合 + 影响逻辑"措辞纪律， 不强行归因——none 是合法且常见的结论
产物生成LLM 组织结构 + 代码渲染 LLM 只产出 ArtifactSpec（结构化中间表示：几章、哪些 block）；文件由确定性渲染器生成。 指标数字不允许 LLM 手写：Excel 全公式、图表数据来自数据集缓存、 事件/变化点按引用挂材料由渲染器注入
质量底线代码（校验层） 溯源回链存在性、事件 URL 真实性（对照检索记录成员校验）、占位符拒绝、 结构约束——渲染前确定性拒绝，报错文案即修正指引，模型在重试循环内自我修正

四、工程实践：事故驱动的防线体系

项目里最有信息量的部分：每一次真实事故 → 一道确定性防线 → 一组还原事故样本的回归测试。 下表全部可在提交历史与测试代码中对证。

真实事故防线（全部确定性，无 LLM 修复调用）
报告里的事件链接全是编造的 404（材料传递丢字段，模型凭记忆造 reuters 链接） evidence 记录检索的全部候选 URL；渲染前对事件 URL 做溯源集合成员校验，报错列出修正指引
子代理单次请求滚到 7.8M tokens 超 8MB 上限；51KB brief 驻留主历史全程陪跑 材料引用传递（值→引用）+ 主历史读时修剪（最近 2 轮完整，旧轮只留对话文本）+ 失败消息截断（错误回显整段参数会翻倍滚雪球）
event-researcher 无预算连搜，达到轮次上限后整体作废（阶段性成果全丢） 检索预算（默认 36 次/运行）：耗尽时工具返回收敛指令而非结果，软着陆保住半途成果
研究完成但最终 JSON 损坏（围栏/野引号/截断），SDK 解析失败 → 整体重跑 三层：submit_events 增量提交（小批量落盘，坏一批只丢一批）→ json_repair 修复链（剥围栏→截花括号窗→迭代转义坏引号→截断数组逐项打捞）→ 兜底合并（Max turns 打满也能用已提交事件返回成功）
换 DeepSeek 官方/Kimi 后 400 连环：response_format 不支持、tool_calls 邻接校验、max_tokens 超上限 llm.py 兼容层唯一收口：json_schema→json_object 降级（schema 改随提示词）、消息序列规整（插队文本并入、回执按序紧随、缺失补占位）、超限自动去参重试。业务代码零供应方分支
早期为控成本设的 12K max_tokens 上限埋雷：spec 内联几十条事件超出输出上限，参数截断 → "Invalid JSON input" 死循环（撞限当时不可诊断） spec 支持 events_material/changepoints_material 按引用挂载，渲染器从工作区注入全量——LLM 不再抄写数据，spec 体积缩 ~90%；同时暴露 finish_reason，"限制"类配置从此配套"撞限可诊断"
Excel"年度收益/核心指标"两表全是字面量"公式"占位符（渲染器没这能力，方法论又禁手写数字） 能力下沉渲染器（年度收益 sheet 按真实年份边界生成公式，行号经 pandas 独立对拍）+ 占位符确定性拒绝
浏览器刷新释放了会话锁，但 SDK 运行没停——幽灵旧轮与新轮并发写同一 session.db 锁生命周期绑定运行任务而非 SSE 连接；停止是真取消（一路到 SDK result.cancel()）；断连只停推送不停任务
界面停在 "run event"，无法判断卡死还是工作（只能看文件 mtime） agent 事件流协议：子代理每次工具调用实时转发到前端时间线/CLI；嵌套运行另落 run_events.jsonl 审计日志供事故复盘

可观测性与日志

  • 三层记录：session.db（对话全量，落库不修剪）/ run_events.jsonl（嵌套 subagent 的工具调用审计——8MB 事故当时只能靠推理还原，之后补的）/ evidence.json（数据溯源）；
  • 事件流 detail 定长截断（错误类放宽到 600 字符——曾把 pydantic 错误切在字段名处导致无法定位）；
  • 前端执行时间线即用户侧日志：历史轮次可回放（从 session.db 重建）。

测试与 CI

  • 自动化测试覆盖核心确定性层，不碰真实网络与 LLM（httpx MockTransport / 打桩事件流 / mock 模式）；
  • 惯例：真实事故必沉淀为"还原事故样本"的回归用例（docstring 标注「真实事故：……」）； 安全设计（路径守卫、权限矩阵、密钥打码）直接写成可执行断言；
  • CI：uv 安装 → ruff → pytest → 前端 install+build+node 测试——每次提交即干净环境可移植性验证； 交付前另做全仓审查（无个人路径/身份，Office 二进制元数据核对）。

五、回顾汇总

做得好

  • 三层边界贯穿始终：每一类事故（编造 URL、占位符、 上下文爆仓、供应方 400）最终都收敛为"一道确定性防线 + 回归测试"，架构没有为任何事故打过补丁式特例；
  • 文档先行真实回本：形态升级、文件安全、传参失真都在写代码前定了原则，后期迭代反复引用；
  • evidence 审计驱动调试：几乎所有疑难问题（检索零命中、假成功、截断死循环）都是先读 evidence/审计日志锁定根因再动代码，而不是猜；
  • ArtifactSpec 中间表示保住产物质量下限：LLM 只产出结构化 spec，不写文件、不手算数字—— Excel 公式联动、PPT 防溢出分页、溯源成员校验全部由渲染器与校验层确定性强制；
  • 材料引用传递贯穿多 agent 协作：事件集、拐点集、任务 brief 等大材料只传 material_id， 子代理按需读取——一套机制同时解决上下文爆仓、跨 agent 传参失真、模型抄写截断三类事故；
  • 应用层文件安全收口：agent 无通用文件读写工具，工具参数只传 artifact_id/dataset_id 逻辑标识，真实路径由系统派生并守卫在会话工作区内；版本文件 append-only、注册表原子写；
  • 增量修改由架构直接保证：spec 中间表示 + 版本化工作区，让"改一处评级"真正只定点变更重渲染、 不重抓数据，历史版本全保留——产品的关键承诺不靠模型配合，靠机制成立；
  • 免 key 可演示：三路资讯源 + 行情多源降级 + 本地缓存，除 LLM key 外零配置， 断网环境也能完整演示核心产物链路；
  • 主动引入外部第二视角并闭环：Codex 独立评审（8/10）暴露的全部问题 （代理环境兼容、文档漂移、校验缺口、CI 缺失）逐项修复并沉淀为回归测试与可复用教训。

做得不足 / 可改进

  • 低估了弱工具调用模型的输出脆性：结构化输出/工具参数的 JSON 损坏问题分了四次才修透 （截断→围栏→野引号→参数内联），如果第一次就把"LLM 输出大 JSON"识别为结构性风险， 材料引用传递会更早成为基础设计；
  • 无真实 LLM 的自动化端到端回归：确定性层全测，但流水线协议改动（如引用传递） 仍靠人工真跑验收——可补一个每日限额的真实冒烟任务；
  • 没有系统性测评集：agent 输出质量（事件相关性、归因合理性、产物完整度）目前靠 人工验收与真实冒烟判断，缺一套可重复打分的评测集来量化不同模型/prompt 改动前后的效果回归；
  • URL 溯源校验目前是全局并集而非逐事件对照（防伪度换误拒率的 v1 权衡）； 事件研究对中文财经资讯实质只有 Tavily 一路，A 股场景可补国内源。

当前限制（如实声明）

  • 单次完整研究任务耗时较长：涉及多路数据采集、事件检索与溯源校准的完整链路，一次真实搜索任务可能需要 15 分钟以上，属深度研究型工作流的固有开销而非缺陷；
  • 国内环境实测仅覆盖 DeepSeek 与 Kimi 两个模型，其他模型未做验证——建议验收时也使用这两个模型；
  • 单用户本地工具：仅 127.0.0.1、无鉴权、单进程内存注册表；
  • 行情依赖 Yahoo 非官方接口（多源降级但无 SLA）；供应方 5xx 无自动重试退避；
  • 子代理无墙钟超时（有轮次上限 + 检索预算兜底）；
  • 产物如需执行用户自定义代码（自定义指标脚本），必须补真沙箱——明确 out of scope。

AI 对话 Prompt 示例（整理版）

以下是从真实开发对话中整理出的三条代表性引导提示词， 分别对应产品形态、架构设计、工程质量三个维度的方向设定。

① 产品形态要求：有状态的研究工作台，产物可交互、可溯源、可增量修改

这个投研 Agent 不要做成"跑一次就结束"的命令工具，我要的是一个有状态的研究工作台。用户用自然语言下达研究任务后，系统自主完成行情采集、变化点检测、事件研究、拐点与事件的对齐归因、产物生成的完整链路；产物要覆盖可交互 HTML（K 线上标记事件、断网也能打开）、全公式 Excel（改参数能联动重算）、PPT 和 Word 报告。最关键的两点：第一，所有结论必须可溯源——每个事件要能回链到真实的检索来源 URL，每个指标要能回链到原始行情数据，不可回溯的结论不允许出现在产物里；第二，支持多轮增量修改——比如我说"把 DeepSeek 事件的评级改成高"，系统应该只定点修改这一处并重新渲染，不能把整个研究流程推倒重跑、重新抓数据，而且历史版本要全部保留，可以随时回看。界面上要像 ChatGPT 那样多会话并行，执行过程中每个 agent 在查什么、算什么要实时可见，运行中可以随时停止。

② 架构设计要求：三层自研划分，判断交给 LLM、事实与纪律交给代码

架构上我明确不用自带 tools/subagents/skills 概念的框架，用 OpenAI Agents SDK 打底，但三层划分要完全自己设计：tools 层只放确定性能力（行情抓取、检索 API、渲染器），subagents 是四个职责单一、上下文互相隔离的判断单元（数据采集、事件研究、对齐分析、报告生成），skills 是可复用的产物方法论资产（方法论文档 + 模板 + 渲染骨架），加载机制自研——我要让"怎么划分一个 agent 系统的边界"体现的是我自己的判断，而不是框架送的结构。划分的总原则是：能用确定性代码解决的绝不交给 LLM。行情拐点是可定义的数学事实，用确定性算法检出，保证可复现、可回归测试；检索本身走确定性 HTTP API，LLM 只决定"查什么"，检索结果不经模型转述；产物文件由代码渲染器生成，LLM 只产出结构化的 spec，数字一律来自公式或数据注入，不允许模型手写。对齐归因这种真正需要语义判断的环节才交给 LLM，但结论必须收敛到受控枚举（match/partial/none），不许强行归因。

③ 工程质量要求：硬要求进校验层，事故驱动测试，不靠 prompt 自觉

质量上我的底线是：所有硬性要求必须落成代码校验，不能写在 prompt 里指望模型自觉遵守。事件 URL 必须逐字出自真实检索记录，模型编造的链接要在落盘前被成员校验拦截；evidence 引用必须真实存在，悬空引用直接拒绝渲染；TBD、待填这类占位符内容不允许出现在正式产物里——校验不通过就没有产物，同时把报错信息设计成能引导模型自我修正的形式。测试策略上，确定性层（工具、渲染器、工作区、校验）单测优先，测试不碰真实网络和真实 LLM；但每层完成后必须做一次真实链路冒烟，专抓 mock 测不出来的问题。每次真实运行暴露的事故，都要沉淀成能还原事故现场的回归测试，修 bug 先去运行日志和会话数据库里找事故现场再动代码，不许凭猜想修。另外供应方兼容问题只在一个适配层收口，业务代码里不许出现任何针对特定供应方的分支判断。
